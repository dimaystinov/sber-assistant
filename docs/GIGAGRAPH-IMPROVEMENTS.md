# Как улучшить GigaGraph для универсального ассистента Сбера

Дата: 9 ноября 2026 года. Это исследование и план, не утверждение о
готовности промышленного банковского решения.

## 1. Что именно улучшать

Репозиторий [ai-forever/gigagraph](https://github.com/ai-forever/gigagraph)
прямо помечен авторами как устаревший форк LangGraph. Они рекомендуют
оригинальный LangGraph вместе с
[`langchain-gigachat`](https://github.com/ai-forever/langchain-gigachat).
Поэтому полезнее улучшать **профиль исполнения GigaChat на LangGraph** и
прикладной граф, чем поддерживать отдельный форк ядра. В этом проекте такой
граф теперь реализован в `assistant/chat_graph.py`.

## 2. Почему обычный агент небезопасен здесь

В шести синтетических сценариях на шести моделях GigaChat инструкции
«не выдумывай» не остановили некоторые модели от описания неподтверждённой
HR-процедуры. В другом ответе модель ошиблась в расчёте процентов. Поэтому
дополнительный агент-критик не может быть последним рубежом: его ошибка может
коррелировать с ошибкой автора. Исследования multi-agent debate фиксируют
[уход обсуждения от задачи](https://aclanthology.org/2026.findings-eacl.268/)
и [общую ошибку нескольких судей на одной базе](https://aclanthology.org/2026.aacl-short.60/).

## 3. Целевая схема

```text
Достоверная идентичность + согласие + роль
  → маршрутизация разрешённого источника
  → evidence gate (документ/живые данные/дата/версия)
  → GigaChat-генератор
  → независимый GigaChat-критик с чистым контекстом
  → детерминированная проверка чисел и разрешённых фактов
  → программное решение: ответ / уточнение / человек

Предложенное действие модели → отдельный tool broker → разрешение кода
  → dry-run и проверка последствий → исполнение / отказ → аудит
```

**Права никогда не определяются голосованием агентов.** Контекст каждого узла
содержит только текущую роль и идентификаторы разрешённых источников.
Переход роли создаёт новую сессию. Системное состояние графа должно содержать
версию политики, версию документа, время извлечения, роль, разрешённые
инструменты, токены и решение каждого gate. LangGraph поддерживает
[отдельные checkpointer и store](https://docs.langchain.com/oss/python/langgraph/persistence);
их ключи должны включать роль и субъект роли, иначе можно смешать память.

## 4. Работа нескольких агентов

### На этапе проектирования

[Elephant Goldfish Model](https://github.com/google/elephant-goldfish-model)
предлагает контекстного автора спецификации и независимых рецензентов,
которым передают документ и источники без предыдущей беседы. Сам репозиторий
говорит, что ревью не заменяет тесты и решение человека. Это хороший способ
проверить модель угроз, границы трёх ролей, критерии полезности и тест-план.
При использовании с материалами банка нужно передавать только разрешённые
синтетические или обезличенные документы. EGM — плагин для процесса разработки,
а не обязательная зависимость работающего ассистента.

### Во время ответа пользователю

В текущем прототипе один GigaChat готовит ответ, второй GigaChat
получает **вопрос, разрешённые источники и черновик без истории диалога** и
ищет только неподтверждённые утверждения, арифметические ошибки и пропущенные
ограничения. Критику не выдаются инструменты записи и данные других ролей.
Если критик нашёл риск, граф возвращает уточнение или передаёт случай человеку;
он не переписывает ответ бесконечно. В прототипе вместо реальной передачи
человеку возвращается сообщение `needs_review`. Две модели одной семьи не дают
независимой гарантии, поэтому постоянный вызов критика нужно сравнить с
выборочным на размеченных сценариях. При отказе или ошибке критика черновик
не публикуется.

Для широкой исследовательской задачи параллельные специалисты могут быть
полезны, но это не означает пользу для каждого короткого банковского ответа:
[описание многoагентной исследовательской системы Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system).

## 5. Безопасный доступ к инструментам

Сейчас граф не передаёт GigaChat инструменты. `assistant/tool_policy.py`
запрещает неизвестные и изменяющие инструменты по умолчанию. Перед выдачей
первого реального инструмента требуется отдельный broker с такими проверками:

1. Идентичность, активная роль, согласие, источник полномочия и срок действия
   проверяются сервером на **каждом вызове**, не по словам модели.
2. Права задаются по конкретному инструменту и ресурсу; список минимален.
   Сначала только чтение. Запись и денежные действия отсутствуют в графе,
   пока нет отдельного согласованного протокола.
3. Результат поиска или чтения считается недоверенным вводом. Инструкции в
   документе не меняют системные правила и права.
4. Для действий с последствиями broker строит проверяемый план и dry-run,
   показывает человеку объект, сумму, адресата и эффект; после подтверждения
   проверяет всё повторно, использует идемпотентный ключ и пишет аудит.
5. Есть лимиты числа вызовов, суммы, времени и размера ответа. При ошибке
   разрешений или недоступности источника граф завершает работу без действия.
6. Отдельные тесты проверяют подмену роли, prompt injection в документах,
   повторный вызов, устаревшее согласие, тайм-аут и частичный сбой.

Эти меры — требования к будущему broker. Текущий прототип **не исполняет**
банковские операции и не обещает абсолютного отсутствия ошибок.

## 6. Что даёт LangExtract

[Google LangExtract](https://github.com/google/langextract) извлекает
структурированные сведения и привязывает извлечённую фразу к точному
символьному интервалу исходного документа. Непривязанное извлечение получает
`char_interval = None`, поэтому его можно отбросить. Это полезно для
подготовки проверяемых фрагментов HR-инструкций, тарифов и договоров.

В библиотеке есть расширяемая система провайдеров, но в опубликованном
[списке community providers](https://github.com/google/langextract/blob/main/COMMUNITY_PROVIDERS.md)
нет готового адаптера GigaChat. Для этого проекта нужен отдельный провайдер,
вызывающий только GigaChat, либо небольшая собственная реализация извлечения
с проверкой символьных интервалов. Gemini из примеров LangExtract в работающий
ассистент подключать нельзя: условие проекта — модели Сбера.

Совпадение фразы с документом доказывает только **наличие текста**, но не то,
что документ актуален, применим к юридическому работодателю и роли или что
вывод модели верен. Поэтому источник должен иметь ID, версию, дату действия,
область применения и подтверждённое происхождение. Без этого evidence gate
не разрешает ответ.

## 7. Приоритет улучшений

| Приоритет | Изменение | Как доказать пользу |
|---|---|---|
| P0 | Настоящая аутентификация, согласия и изолированная память | Ноль пересечений ролей на adversarial-наборе |
| P0 | Источники с происхождением и сроком актуальности | Ноль внутренних процедур без подтверждённого документа |
| P0 | Арифметика кодом, проверка результата | Ноль неверных расчётов на размеченном наборе |
| P0 | Tool broker с запретом по умолчанию | Ноль исполненных неразрешённых действий |
| P1 | Выбор модели по роли и сложности | Лучшая полезность при заданных задержке и токенах |
| P1 | Выборочный независимый критик | Снижение пропущенных ошибок против простого графа |
| P2 | Длительная память и многошаговые планы | Улучшение многоходовых задач без утечки ролей |

## 8. Как проверять гипотезу о критике

Нужен размеченный набор по трём ролям: ответы с отсутствующим источником,
устаревшим документом, неверным числом, ложным доступом к счёту, попыткой
пересечь роль и вредным советом. Сравнить четыре варианта при одинаковых
GigaChat-моделях: (A) один генератор, (B) генератор + программные gates,
(C) B + GigaChat-критик, (D) C + передача человеку на спорных случаях.
Измерять опасные пропуски, ложные блокировки, полезность следующего шага,
задержку и токены. Результат надо оценивать по проверяемому эталону и экспертной
разметке, а не только по мнению ещё одной модели. Это следует также из
[Harness-Bench](https://arxiv.org/abs/2605.27922): измеряют конфигурацию
модель + harness, а не только базовую модель.
