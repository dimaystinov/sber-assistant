# MCP для трёхролевого ассистента Сбера

**Статус на 10 ноября 2026 года:** учебный in-process MCP-клиент и ролевой MCP-сервер подключены для `search_knowledge`, `read_demo_data` и `calculate_cash_gap`. Дополнительно созданы локальные двойники **пяти официально документированных MCP-сервисов Sber API** и отдельные вымышленные адаптеры CRM/HR/ИТ/регламентов; см. [исследование и результаты](SBER-MCP-SIMULATION.md). Чтение охватывает учебные счета, выписки, статусы платежа, инкассацию, предложения, CRM и внутренние вопросы. Серверный gateway проверяет роль, согласие и scope. Учебный платёжный черновик требует отдельного подтверждения. Подготовлен [read-only mTLS-коннектор](SBER-OFFICIAL-SANDBOX.md) к пяти фиксированным адресам официальной песочницы; локальный handshake проверен. Удалённые MCP-серверы Сбера и реальные банковские данные пока не подключены из-за отсутствия выданных банком `.p12` и `access_token`.

## Что подключать

| Приоритет | MCP-сервер / возможность | Польза по ролям | Условие подключения |
|---|---|---|---|
| 1 | **Собственный knowledge MCP**: `search_policy`, `read_source`, `get_version` | Все роли; сотруднику — утверждённые регламенты | Фильтр роли, владельца, статуса и срока документа **до** поиска; цитата с версией и фрагментом; отказ при отсутствии основания |
| 1 | **Официальные MCP-сервисы Sber API**: информация о клиенте, выписка, платежи, инкассация, депозиты/НСО | Предприниматель | Договор, TLS-сертификат, access token, согласованные scopes; сначала официальная песочница |
| 1 | **Собственный read-only CRM/HR/ИТ MCP**: лиды, задачи, процедуры | Предприниматель, сотрудник | Реальная идентичность и права; схема внутреннего сервиса от владельца процесса; запрет доступа к чужим данным |
| 1 | **Собственный calculator MCP**: деньги, проценты, маржа, бюджет, сравнение вариантов | Все роли, особенно бизнес | Decimal/формальные формулы, единицы измерения, тесты граничных значений; модель объясняет только проверенный результат |
| 2 | **Собственный action MCP**: корзина, бронь, рекламный черновик, задача сотруднику | По разрешённой роли | Отдельные `prepare_*` и `confirm_*`, явное подтверждение человека, одноразовый токен и идемпотентность, журнал аудита |
| 2 | **Официальный Sber docs-mcp** | Разработчики и поддержка интеграции GigaChat | Только документация API, не источник клиентских тарифов или внутренних правил |
| 3 | **MCP Voice Salute** | Голосовой канал и доступность интерфейса | Согласие на аудио, обработка ПДн и проверка транскрипта перед действием |
| 3 | **MCP Kandinsky** | Черновики рекламных материалов предпринимателя | Права на контент и отдельное согласование публикации |
| исследование | **Think MCP** | Организация промежуточного рассуждения | Не считать доказательством правильности; не открывать ему секреты и операции |
| не по назначению | **MCP Giga Checker** | Выявление признаков машинного текста | Не использовать как критика фактов или юридический контроль |

Последние четыре проекта перечислены в [репозитории GigaChain](https://github.com/ai-forever/gigachain); [docs-mcp описан в документации Сбера](https://developers.sber.ru/docs/ru/gigachat/guides/using-docs-with-llm). Собственные банковские MCP-серверы в таблице — **предлагаемые адаптеры**, их нет в публичном API проекта и они не являются продуктами Сбера.

## Правильное место MCP в harness

```text
Пользователь → идентичность/роль/согласие → планировщик GigaChat
          → policy broker (allowlist, scope, schema, лимит, аудит)
          → MCP client → ролевой учебный MCP server → проверка результата
          → GigaChat-генератор → независимый GigaChat-критик
          → программные gates → ответ или эскалация
```

Разделять **MCP resources** (проверенные документы и данные), **tools** (вычисления и действия) и **prompts** (подсказки оператору) следует согласно [официальному Python SDK](https://py.sdk.modelcontextprotocol.io/get-started/first-steps/). Ресурс и результат инструмента — данные с более низким доверием, чем серверная политика. Текст документа не может менять права и командовать следующими вызовами. [Официальная документация Sber API](https://developers.sber.ru/docs/ru/sber-api/mcp/mcp-payment) подтверждает реальные MCP endpoints и scopes, поэтому при переходе к банковскому стенду нужно подключать именно их, а не придумывать собственный payment API.

Пример [GigaChain + `langchain_mcp_adapters`](https://github.com/ai-forever/gigachain/blob/master/cookbook/mcp/agent.py) подтверждает техническую совместимость GigaChat и MCP-инструментов. Его прямой ReAct-вызов всех загруженных tools и отключённая проверка TLS **не подходят** для банковского контура: broker обязан отфильтровать функции до передачи модели и проверить каждый вызов на сервере. [Сбер описывает GigaChat function calling как основу MCP-архитектуры](https://developers.sber.ru/help/gigachat-api/model-context-protocol).

## Контракт одного вызова

1. Сервер устанавливает субъект, роль, tenant, цель, согласие и разрешённый scope вне текста модели.
2. Broker раскрывает только подходящие функции и ограничивает число шагов, время, расходы и область данных.
3. Аргументы проходят JSON Schema и бизнес-валидацию. Идентификаторы объектов проверяются по правам субъекта заново на каждом вызове.
4. Read-only запрос возвращает структурированный результат, время, источник и версию. Ошибка/неполнота ведёт к уточнению или отказу.
5. Изменение состояния начинается с `prepare`: точный payload, цена и последствия показываются человеку. `confirm` принимает одноразовый токен, связан с субъектом и payload, поддерживает идемпотентность.
6. Аудит хранит решение policy, версии модели и документа, аргументы в разрешённом объёме и итоговое состояние. Не записывает секреты и лишние ПДн.

В удалённом MCP нужны проверка токена и scopes по [спецификации авторизации](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) и защита от prompt injection, SSRF, подмены сервера и чрезмерных полномочий по [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html). Внутренний сервер должен быть размещён в разрешённом контуре; нельзя отправлять клиентские данные в случайный публичный MCP.

## Очерёдность внедрения

Первый шаг выполнен на учебных данных: knowledge, calculator, read-only инструменты и двойники Sber API через MCP; учебный `create_invoice` также находится за `prepare/confirm` и создаёт только неподписанный черновик. Далее — подключение **официальной песочницы Sber API** по выданным TLS/токену/scopes, проверка фактических схем и статусов, затем закрытый пилот под контролем владельцев процессов. На каждом этапе сравнивать полезность, точность источников, отказ при отсутствии права, повторный вызов и фактическое состояние после операции. Нынешний сервер создаётся внутри процесса на каждый вызов; это доказывает работу протокола, но для промышленной нагрузки потребуются постоянные соединения, авторизованный удалённый transport и тесты отказоустойчивости. [Банковская песочница](https://developers.sber.ru/docs/ru/sber-api/start/sandbox) допускает функциональную проверку, но не нагрузочные тесты. Ни один MCP не заменяет проверку регламента, законодательства РФ и квалифицированного специалиста для регулируемой консультации.
